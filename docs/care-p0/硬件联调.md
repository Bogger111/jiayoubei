# 最小硬件联调

当前状态：待实物验证。以下是联调操作包，没有进行接线、烧录或物理动作核验。

## 器材与连接

先核对板上型号。`examples/care/esp32-care.yaml` 仅是经典 ESP32 DevKit 示例；C3、S3、ESP8266 需按实际引脚重新配置。

| 项目 | 示例引脚 | 用途 |
| --- | --- | --- |
| 回应按钮 | GPIO19 与 GND，输入上拉 | 记录“有人按下”，不自动归属具体人，也不自动结案 |
| 求助按钮 | GPIO21 与 GND，输入上拉 | 新鲜明确求助优先进入人工核实 |
| 活动传感器 | GPIO27 | 按传感器规格接电，只将兼容 3.3V 的输出接入 GPIO |
| 干接点门磁 | GPIO22 与 GND，输入上拉 | 门的开关观察，不确认某人已经离家 |
| LED | GPIO18 经限流电阻连接 LED 与 GND | 低风险物理输出，建议 330Ω；按 LED 极性连接 |

不必一次接齐：两只按钮和 LED 即可验证最小链路，门磁与活动传感器可随后接入。按钮模板含去抖。

## 配置顺序

1. 在 ESPHome 中校验实际板型、引脚、WiFi 和 API 加密配置。实际密码保存在本地 secrets.yaml，不放入仓库；本项目旧 `esphome/` 私有配置保持隔离。
2. 接入 HA 后，用 HA 实际显示的实体 ID 替换 `examples/care/care.env.example` 中的名称。
3. 用应用中的真实成员 ID 替换 REPLACE_MEMBER_ID；在关怀确认页约定联系人、静默阈值和午休时间。
4. 复制配置为根目录 `.env.care.local`。配置 HA URL/Token、采集密钥、白名单、家庭 ID 和唯一采集批次 ID。Worker 的私有 `.dev.vars` / secrets 需配置相同采集密钥及实体映射；桥接器和 Worker 不是共享一个自动配置文件。
5. 首次台架将 CARE_CAPTURE_CATEGORY 设为 bench。假服务测试用 synthetic，知情角色演练用 reenactment，自然家庭使用才用 field。
6. 启动应用后运行：`node --env-file=.env.care.local scripts/care/ha-bridge.mjs`。
7. 打开 `/care`。桥接器只采集白名单实体，原始观测和未送达队列保存在被 Git 忽略的 `.care-local/`。

## 必须实际核验的闭环

真人按钮/传感器输入 → 页面出现来源与时间 → 形成待确认计划 → 家属批准 → 实际 LED 变化 → 另一位真实成员账号查看并接手 → 明确记录结果 → 未执行的后续联系停止。

灯亮需由现场观察者记录时间和方式；HA 接口 200 或 state=on 不是独立的物理效果证据。联调服务调用 `/api/services/light/turn_on`，不通过 POST `/api/states` 修改显示状态冒充控制。

回应按钮只证明该按钮被按过。联系人的明确结果仍需记录确认人、方式、当前事件和是否已核实。多人场景不能由按钮自动识别按下者。

## 故障核验

- 拔掉输入设备：应显示信息缺失，不能把掉线当成无人活动。
- 设备离线但按下另一来源的求助按钮：仍应优先进入人工响应。
- 网络中断：桥接器保留原始事件 ID，恢复后重送；服务端去重。
- 执行时服务中断：未确定的动作标为未知，不自动重复触发；现场核对实际效果。
- 回复和等待期限同时发生：最终状态只能是一份；已经发出的动作如实保留，未发出的安排停止。
- 重启应用：任务、确认、截止时间应恢复。云端自动推进需要部署包含 cron 的 Worker；本地工作台打开时也会检查到期安排，不能将本地页面轮询说成已部署的后台服务。
